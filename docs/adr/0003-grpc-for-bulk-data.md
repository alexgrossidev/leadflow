# 0003: gRPC streams for bulk data, events for facts

**Status:** accepted

## Context

Two flows move large volumes between services:

- When a user creates an automation, every existing lead that matches must be enrolled. That can be tens of thousands of rows.
- A bulk import delivers parsed rows to the service that owns customers.

Putting each row on a queue would multiply queue traffic and lose ordering and flow control. A plain REST call with a giant response body would buffer everything in memory on both sides.

## Decision

Use gRPC for these data transfers, with contracts in `packages/rpc/src/proto` and code generated by buf and ts-proto:

- `LeadService.GetLeadWithFilters` is a **server stream**. The gateway pages through MySQL with keyset pagination and waits for `drain` when the client falls behind. The client consumes with `for await` and enrols in batches.
- `CustomerService.BulkInsertCustomers` is unary, one batch per call. It is retried only on `UNAVAILABLE`, because other failures aren't safe to repeat blindly.

Facts ("this happened") stay on the event bus.

## Consequences

- Memory stays bounded on both ends regardless of result size, and backpressure propagates from the consumer to the database cursor.
- Every call sets a deadline, and errors are mapped so internal details never cross the wire.
- **Cost:** a second transport to operate, and generated code to keep in sync. CI regenerates the code and fails on drift.
- **Cost:** the filter semantics exist twice: in the gateway's SQL filter and in automations' in-memory matcher for live events. Both follow one written specification, and both are tested against it.
